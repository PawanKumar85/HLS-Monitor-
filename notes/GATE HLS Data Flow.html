HLS Data Flow

How a stream gets registered, checked, streamed to the browser, saved and summarised, how the multi-hop pipeline finds the root cause, and how alerts reach a device even when the site is closed. Every key, limit, and collection name below is taken from the current code.

  1. 0Sign in

    Every page and API needs a signed-in user (/login, passport-local); only /health and the push service worker /sw.js are open. Sessions live in Redis for 12 hours. There are no roles.

  2. 1Register

    Streams enter through /api/streams (no page of its own any more). Channel hops built on Add Stream register their HLS URL here as pipeline:<channel>/<hop>. Edits need the current version in If-Match.

  3. 2Store

    MongoDB holds the real list of streams. The sync worker copies changed rows to Redis every second and retries failures with backoff.

  4. 3Schedule

    Redis keeps each stream's next check time. Every 500 ms the scheduler queues up to 50 due streams, one job each, unless a job is already waiting.

  5. 4Queue

    Each server gets its own Redis Stream, hls:streams:<serverIp>, so one busy server doesn't delay the rest. Jobs older than an hour are trimmed.

  6. 5Consume

    One consumer per server runs a pool of 10 checks, so a stream that times out holds only its own slot, not the whole batch.

  7. 6Check

    Fetches the playlist and requests the first 1 KB of a segment, stopping after the first nonempty chunk, and checks the playlist is still advancing. Offline after two failures in a row or a frozen playlist; each offline check records why (TIMEOUT, DNS, HTTP_404, FROZEN…).

  8. 7Batch

    Results wait in memory per server. The batch is sorted by time and written at 7 MB or every 5 seconds.

  9. 8Save

    Rows go to hls_stream_metrics and are kept 7 days. A message is acknowledged only after the write succeeds.

  10. 9Pipeline

    Channels and their hops are drawn on the Add Stream canvas. Every 10 s the monitor reads each HLS hop's live status, connects to TCP hops and pings SRT hosts. The first hop down is the root cause; a host that breaks several channels opens one incident.

  11. 10Reports

    Every minute the raw checks are summarised into hls_stream_hourly. Reports reads only those rows: availability, downtime, outages, MTTR, p95/p99 of online checks and failure reasons, plus a per-server outage log and hourly bars. Cached 60 s.

  12. !Alerts

    Incidents (root cause, channel down, VOD fallback) and the watchdog's "Monitoring stopped" go to the webhook and, via Web Push, to every device that turned alerts on in Account, even with the site closed. Best effort: the dashboard stays the record.

  13. !Failures

    Messages that fail 5 times move to hls:dlq:<serverIp>, then in bulk every 5 s to hls_processing_failures (resolved ones deleted after 30 days). The DLQ page shows them live within ~10 s, with whole-history counts, search, grouping and a confirmed replay.
